# 设计知识库 · 字段与 Key 设计（v0.2）

> 目标：落地 4 元组「设计意图 → 主图特征 → 设计内容 → 示例图」。
> v0.2 变更：`heroFeatures` 从结构化描述改为**匹配标签**（两桶：硬过滤 facets + 语义 semanticTags）；`design` 改为**描述文本优先**；新增预设标签词表与「硬过滤→语义召回→重排」检索策略。

---

## 1. 定位与四元组映射

| 用户四元组 | 顶层字段 | 本质 | 说明 |
|---|---|---|---|
| 设计意图 | `intent` | 受控词表 + goal | 要传达什么、什么调性、投哪 |
| 主图特征 | `heroFeatures` | **匹配标签**（facets + semanticTags） | 这张图「是什么」，靠标签在检索时匹配 |
| 设计内容 | `design` | **描述文本**（可被模型改写） | 这类图该怎么设计，作为 L2 few-shot 的一部分 |
| 示例图 | `image` | 原图 / 缩略图 | 视觉参考 |

**核心认知（与用户对齐）**：
- 主图特征是**语义匹配标签**，不是结构化 SceneAnalysis 的完整复刻；检索时靠标签（硬过滤）+ 向量（语义近义）匹配。
- 设计内容是一段「设计如何进行的描述文字」，注入 L2 后**可能被模型改写、再重生成**——这是合理步骤，KB 是 few-shot 种子，不是死模板。

---

## 2. 顶层结构与 Key 约定

```jsonc
{
  "id": "case_ms_000123",
  "schemaVersion": 2,
  "source": { /* 溯源 */ },
  "intent": { /* 设计意图 */ },
  "heroFeatures": { "facets": {}, "semanticTags": [] },   // 主图特征 = 匹配标签
  "design": { /* 设计内容 = 描述文本 */ },
  "image": { /* 示例图 */ },
  "quality": {},      // 质量信号（含负例标记，见 §9）
  "embedding": {}
}
```

### Key 约定

| Key | 规则 | 示例 |
|---|---|---|
| `id` | `case_<sourceSlug>_<6位序号>` | `case_ms_000123`、`case_vg_000045`、`case_in_000007` |
| `source.type` | `motionsites.ai` / `vogue` / `elle` / `poster` / `web` / `internal` | — |
| `schemaVersion` | 结构变更 +1 | 当前 2 |
| 硬过滤 key | `heroFeatures.facets.*` | 见 §4 |
| 语义召回 key | `heroFeatures.semanticTags` + `intent.goal` + `design.description` | 进文本向量 |

来源缩写：`ms`=motionsites.ai，`vg`=vogue，`el`=elle，`pt`=poster，`wb`=web，`in`=internal。

## 3. 字段明细

### 3.1 `source`（溯源，必填）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | enum | ✅ | 受控来源类型 |
| `url` | string | ✅ | 原始页面 URL |
| `title` | string | — | 原作品标题 |
| `capturedAt` | ISO8601 | ✅ | 抓取时间 |
| `license` | enum | ✅ | `reference-only` / `open` / `internal` |

### 3.2 `intent`（设计意图，必填）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `goal` | string ≤40 字 | ✅ | 一句话：要传达的核心信息/情绪（自由，只写「要什么」不写「怎么做」） |
| `tone` | enum[] | ✅ | 调性（受控，§4） |
| `messageType` | enum | ✅ | 信息类型（受控，§4） |
| `platform` | enum | ✅ | 投放媒介（受控，§4） |
| `audience` | string ≤20 字 | — | 目标人群 |

### 3.3 `heroFeatures`（主图特征 = 匹配标签，必填）

```jsonc
{
  "summary": "一句话画面概括（可空，用于文本向量兜底）",
  "facets": {                    // 受控「硬过滤标签」：每维度是数组（可多值），集合重叠匹配
    "subjectType": ["单人"],
    "gender": ["女"],
    "subjectRatio": ["大占比"],
    "scene": ["户外自然", "旅行出游"],
    "vertical": ["旅行攻略", "探店打卡"],
    "photoStyle": ["生活照"],
    "light": ["自然光"],
    "mood": ["温情治愈"]
  },
  "semanticTags": [              // 「语义召回标签」：自由 + 近义/上位，进文本向量
    "旅游搭子", "旅行出游", "自然光人像", "女性时尚穿搭"
  ]
}
```

**两桶的区别（关键）**：

| 桶 | 匹配方式 | 例子 | 能否自由新增 |
|---|---|---|---|
| `facets` 硬过滤 | 集合重叠（维度内 OR、维度间 AND） | vertical=[穿搭时尚,探店打卡] | ❌ 只能从 §4 预设词表选 |
| `semanticTags` 语义召回 | 向量近义/上位 | 「旅游搭子」↔「旅行攻略」↔「结伴出游」 | ✅ 自由，落库时 LLM 生成 |

> 性别标签仅用于**匹配/检索**，不用于任何敏感的下游决策，避免产生歧视性输出。

> **多值标签**：每个 `facets` 维度是数组，可打多个 tag（如 `vertical:["穿搭时尚","探店打卡"]`）。检索时**维度内任一命中即算（OR），维度之间都要满足（AND）**。自然单值的维度（如 `subjectRatio`）就填单元素数组。`semanticTags` 本就是数组，无限制。

### 3.4 `design`（设计内容 = 描述文本，必填）

> 设计内容的**第一形态是描述文字**：一段「这类图该怎么设计」的说明，注入 L2 提示词后被模型参考，可能部分改写、再重生成。结构化 `spec` 只作为可选附加，不强制。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `description` | string ≤300 字 | ✅ | 设计如何进行的描述：文案层级/字体/字号/对齐/留白/配色/动效/锚点倾向 |
| `spec` | DesignSpec | — | 可选：若能还原成结构化 spec 则存，否则留空 |
| `prompt` | string | — | 可选：源站原始生成提示词（motionsites.ai 有），保留作原始依据 |

描述文本写法约定：只写「做法」，不写「这张图长什么样」（画面特征属于 heroFeatures）。示例见 §6。

### 3.5 `image`（示例图，必填）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `kind` | enum | ✅ | `full`（存原图，网页截图）/ `thumbnail`（存缩略图，杂志） |
| `path` | string | ✅ | 本地相对路径 |
| `thumbPath` | string | — | `kind=full` 时附一份缩略图 |
| `width` / `height` | int | ✅ | 像素 |
| `format` | string | ✅ | `png`/`jpg`/`webp` |
| `url` | string | — | 原始外链 |

## 4. 预设标签词表（每属性约 10 个，作为种子，可增量扩展）

> 与动效目录同理：**单一事实源 + 版本号**，新增受控标签必须登记，否则落库新旧不一致、检索 key 漂移。

### 4.1 `heroFeatures.facets` 维度（主图特征 · 硬过滤）

| 维度 | 预设值（约 10 个） |
|---|---|
| `subjectType` 主体类别 | 单人 / 双人 / 多人 / 商品特写 / 美食 / 建筑空间 / 自然风景 / 动物 / 静物 / 无主体 |
| `gender` 主体性别 | 男 / 女 / 中性 / 男女双人 / 男性为主 / 女性为主 / 多人混合 / 儿童 / 老人 / 无人物 |
| `subjectRatio` 主体占比 | 特写 / 半身 / 全身 / 大占比 / 中占比 / 小占比 / 远景 / 无主体 |
| `scene` 拍摄场景（视觉） | 生活化日常 / 城市街拍 / 室内居家 / 户外自然 / 旅行出游 / 运动健身 / 办公商务 / 餐饮探店 / 夜店派对 / 影棚棚拍 |
| `vertical` 营销垂类（业务） | 商品带货 / 旅行攻略 / 穿搭时尚 / 宠物萌宠 / 美食餐饮 / 探店打卡 / 演出音乐 / 户外运动 / 健身塑形 / 母婴亲子 / 美妆个护 / 家居生活 / 汽车出行 / 数码科技 / 民宿酒店 / 本地生活服务 |
| `photoStyle` 照片风格 | 生活照 / 街拍 / 时尚大片 / 胶片复古 / 纪实 / 极简 / 潮流潮牌 / 日系清新 / 欧美杂志 / 证件照 |
| `light` 光线时间 | 白天 / 黄昏 / 夜晚 / 室内暖光 / 自然光 / 人造光 / 逆光 / 阴天 / 晴天 / 弱光 |
| `mood` 情绪调性 | 温情治愈 / 高级简约 / 活力动感 / 复古潮流 / 街头酷感 / 奢华精致 / 自然质朴 / 科技未来 / 趣味幽默 / 安静文艺 |

> 区分：`scene` 是**画面在哪儿拍**（视觉），`vertical` 是**这张图做什么营销**（业务）。例：旅行照 `scene=户外自然`、`vertical=旅行攻略`；宠物图 `scene=生活化日常`、`vertical=宠物萌宠`；穿搭图 `scene=城市街拍`、`vertical=穿搭时尚`。

### 4.2 `intent` 维度（设计意图 · 受控）

| 维度 | 预设值 |
|---|---|
| `tone` 调性 | 暗调质感 / 明亮清新 / 复古潮流 / 街头潮流 / 温情治愈 / 趣味对比 / 高级简约 / 赛博科技 / 自然质朴 / 奢华精致 |
| `messageType` 信息类型 | brand-slogan（品牌口号）/ product-selling-point（单品卖点）/ emotional-mood（情绪短句）/ event-promotion（活动促销）/ location-season（地点+季节）/ story-narrative（故事叙事） |
| `platform` 媒介 | web-hero / landing / poster / magazine-cover / xhs-3x4 / story-9x16 / cover-4x3 |

### 4.3 `semanticTags`（语义召回 · 自由，落库时生成）

不设枚举；由标签生成环节（LLM）从「画面 + 意图」抽取近义/上位标签，例如 `旅游搭子` / `旅行攻略` / `结伴出游` 都指向同一语义簇，靠文本向量互相召回。

## 5. 检索策略：硬过滤 → 语义召回 → 重排

```
新照片/创作方向
   ↓ intent-inference（后续环节，§7）
intent + heroFeatures(facets + semanticTags)
   ↓ ① 硬过滤：facets 集合重叠（维度内 OR、维度间 AND；性别/主体类别/占比/场景/光线…）
   ↓ ② 语义召回：semanticTags + intent.goal + design.description 的文本向量近邻（Top-N，宽松）
   ↓ ③ 重排：按 quality / 相关度 / 平台一致性重排，取 3–5 条
   ↓ 注入 L2 作为 few-shot（设计内容描述文本）
```

用户提到的「重排可能没了」正是 ②→③ 的正常现象：语义召回放宽、重排收紧，允许近义标签被召回后又在重排中被淘汰。

## 7. 与「意图识别环节」的衔接（后续再做）

未来 `intent-inference` 步骤：新照片/创作方向 → 产出 `intent` + `heroFeatures.facets` + `semanticTags`（对齐 §3.2/§3.3）→ 作为检索 key。本 schema 已把三者独立成字段，届时只需实现该步骤的输入输出，检索层不改。

## 8. 图片落库策略（已确认）

| 来源 | 策略 |
|---|---|
| 网页截图（motionsites.ai / 通用 web） | 存原图 `kind=full` + 缩略图 |
| 杂志/海报封面（vogue / elle / poster） | 存缩略图 `kind=thumbnail` + 详细 `design.description` |
| 所有记录 | 保留 `source.url` / `capturedAt` / `license` |

## 9. 数据质量与遗漏项（v0.2 新增）

落库与检索要同时满足，否则「召回认可率 ≥70%」无法衡量：

1. **负例与质量信号**：`quality` 需支持 `accepted` / `bad` 标记，用于负采样和评估召回好坏；「检索案例是否被采纳」要回流。
2. **三元一致性门**：`intent` ↔ `heroFeatures` ↔ `design` 必须自洽（这段设计就是针对这类图、这种意图的做法）；落库时校验，避免召回「看着像但做法不相关」的案例。
3. **标签生成可校验、可回流**：`facets` 落库时做枚举夹取（非法回退默认并记 issue）；`semanticTags` 自由但标注来源/置信度，人工校正后回流（对齐 PRD P12 闭环）。
4. **注入预算**：few-shot 条数（3–5）+ token 上限要在注入处控制，避免 prompt 膨胀（对齐 PRD 的「提示词膨胀→遵循度下降」）。
