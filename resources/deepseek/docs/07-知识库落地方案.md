# 设计知识库落地方案（v1.0）

> 面向**任何模型与平台**的通用实现方案：不绑定特定厂商、框架或编程语言；所有关键概念在 §0 给定义。
> 关联：字段设计见 `docs/06-设计知识库字段设计.md`（本文件是「怎么落地」，那是「存什么」）。

---

## 0. 术语表（供外部读者对齐）

| 术语 | 定义 |
|---|---|
| 稀疏检索 sparse | 词法/关键词/精确元数据匹配，代表：BM25、SQL `WHERE`、FTS 全文检索 |
| 稠密检索 dense | 把文本/图转成向量，按余弦相似度召回，代表：embedding + 向量库 |
| 混合检索 hybrid | 稀疏 + 稠密并行召回后融合排序 |
| RRF 融合 | Reciprocal Rank Fusion：`score = Σ 1/(k + rank_i)`，把多路排序合并，无需调权 |
| facet | 受控元数据标签，枚举值、精确匹配（如「性别=女」） |
| semanticTag | 自由语义标签，靠向量近义匹配（如「旅游搭子」↔「旅行攻略」） |
| few-shot 注入 | 把召回案例的设计描述拼进提示词，作为参考示例 |
| 重排 rerank | 对召回结果二次排序，收紧结果集 |

---

## 1. 目标与边界

**目标**：建成一个「设计意图 → 主图特征 → 设计内容 → 示例图」四元组知识库，用**稀疏+稠密混合检索**按需召回，把召回案例的「设计内容描述」作为 few-shot 注入设计师（L2）提示词。

**非目标（本阶段不做）**：在线微调模型、生成式重绘、把知识库当训练集、公开分发。

---

## 2. 数据模型（四元组，精简版）

> 完整字段见 `docs/06`。此处给自包含的核心结构，`case.schema.json` 是唯一机器可校验的事实源。

```jsonc
{
  "id": "case_ms_000123",           // 唯一主键 case_<来源缩写>_<6位序号>
  "schemaVersion": 2,
  "source": { "type": "motionsites.ai", "url": "...", "capturedAt": "...", "license": "reference-only" },
  "intent": {                        // ① 设计意图
    "goal": "传达科技产品的专业感",    // 自由，≤40字，只写「要什么」
    "tone": ["高级简约"],             // 受控
    "messageType": "brand-slogan",    // 受控
    "platform": "web-hero"            // 受控
  },
  "heroFeatures": {                  // ② 主图特征 = 匹配标签
    "summary": "一句话画面概括",
    "facets": { "subjectType": ["单人"], "gender": ["女"], "scene": ["生活化日常"], "vertical": ["旅行攻略"] }, // 受控元数据（数组可多值）
    "semanticTags": ["旅游搭子", "旅行出游", "自然光人像"]                      // 自由语义
  },
  "design": {                        // ③ 设计内容 = 描述文本
    "description": "这类图该怎么设计的描述文字（会被模型参考/改写）",
    "spec": null,                    // 可选：结构化 DesignSpec
    "prompt": null                   // 可选：源站原始提示词
  },
  "image": { "kind": "full", "path": "cases/.../hero.png", "width": 1920, "height": 1080 },
  "quality": { "human": 4.5, "accepted": true },
  "embedding": {}
}
```

## 3. 标签体系与版本管理

### 3.1 两类标签

| 类型 | 匹配方式 | 能否自由新增 | 用途 |
|---|---|---|---|
| `facets` 受控元数据 | 集合重叠（维度内 OR、维度间 AND） | ❌ 只能来自标签目录 | 硬过滤 |
| `semanticTags` 自由语义 | 向量近义/上位 | ✅ 落库时由 LLM 生成 | 语义召回 |

> **多值**：词表（§3.2）是「允许值集合」；单条案例里每个 `facets` 维度存**数组**，可多值（如 `vertical:["穿搭时尚","探店打卡"]`）。检索时维度内 OR、维度间 AND。

### 3.2 标签目录（唯一事实源 + 版本）

独立文件 `kb/catalog/tags.json`，带 `version`：

```jsonc
{
  "version": 3,
  "facets": {
    "subjectType": ["单人","双人","多人","商品特写","美食","建筑空间","自然风景","动物","静物","无主体"],
    "gender": ["男","女","中性","男女双人","男性为主","女性为主","多人混合","儿童","老人","无人物"],
    "subjectRatio": ["特写","半身","全身","大占比","中占比","小占比","远景","无主体"],
    "scene": ["生活化日常","城市街拍","室内居家","户外自然","旅行出游","运动健身","办公商务","餐饮探店","夜店派对","影棚棚拍"],
```

### 3.3 版本与同步规则（用户明确要求）

1. 系统**永远读取最新版本**的 `tags.json`。
2. 标签改动（增/删/改名/合并）必须在 `migrations` 登记，`version` +1。
3. 改动触发**回填**：迁移脚本遍历存量案例，把旧标签替换/重新生成，避免「时间差造成不准」。
4. 落库时 `facets` 值若不在当前目录内 → 记 issue 并回退默认，禁止静默写入脏标签。

## 4. 检索架构：稀疏 + 稠密混合（三段式）

```
查询(新照片/创作方向)
  → 意图识别 intent-inference（后续环节，先手工/规则给）
  → ① 硬过滤：facets 集合重叠（维度内 OR、维度间 AND；SQL 用 IN + 交集）
  → ② 混合召回：并行跑「稀疏词法」+「稠密语义」，RRF 融合
       - 稀疏：BM25/FTS5 对 design.description + intent.goal + semanticTags
       - 稠密：embedding 向量对 semanticTags + summary + description
  → ③ 重排：按 quality.human / accepted / platform 一致性收紧，取 3–5 条
  → few-shot 注入 L2
```

要点：
- ① 是**确定性过滤**，不会因为向量相似而混入「性别不对」的案例。
- ② 中「旅游搭子↔旅行攻略」这类近义，由稠密召回覆盖；「产品名精确命中」由稀疏覆盖。
- ③ 允许近义案例被召回后又在重排中被淘汰（用户已确认这是正常现象）。

## 5. 落库流程（Ingest Pipeline）

```
采集(爬虫/截图) → 解析(标题/正文/图) → 标签生成(LLM) → 校验 → 落库(元数据 + 向量) → 质量标记
```

各环节职责与校验：

| 环节 | 产出 | 校验/回流 |
|---|---|---|
| 采集 | 原图/缩略图 + `source` | 尊重 robots.txt；Elle 禁 AI 爬则不爬；记录 `capturedAt`/`url` |
| 解析 | 标题、描述、原始提示词 | 结构完整才入库 |
| 标签生成 | `facets` + `semanticTags` + `intent` | `facets` 枚举夹取；`semanticTags` 自由但标来源/置信度 |
| 落库 | 记录 + 向量 | 三元一致性门（意图↔特征↔内容自洽） |
| 质量标记 | `quality.accepted` | 人工校正/采纳回流 |

---

## 6. 检索与注入流程

```
查询 → 混合检索(§4) → 重排 → 取前 3–5 条 → 把 design.description 拼成「参考案例」段 → 注入 L2 提示词
```

- **注入预算**：few-shot 条数 3–5、总 token 上限，防止 prompt 膨胀。
- **改写回流**：模型改写了某条设计描述、或用户采纳了某条 → 回流更新该案例（`quality` + 描述）。
- **负面案例**：低优先级，先写在 Agent 角色提示词（系统提示）里作为禁令；后续再以 `quality.accepted=false` / `quality.bad=true` 落库用于负采样。

## 7. 技术选型（可替换，给出起步默认）

| 能力 | 起步默认 | 扩展/替换 |
|---|---|---|
| 存储 + 稀疏词法 + facets 过滤 | **SQLite**：FTS5（BM25 全文）+ SQL `WHERE`（facets） | PostgreSQL + pgvector |
| 稠密向量 | **sqlite-vec**（本地向量扩展） | Qdrant / Milvus / pgvector |
| 文本嵌入 | 任意多语言 embedding 模型（如 bge-m3 / text-embedding-3） | 可换 |
| 图像嵌入（可选） | CLIP 系（视觉召回，可后置） | 可换 |
| 标签生成 | 任意 LLM 结构化输出（`response_format=json`） | 可换 |
| 重排 | 规则打分（质量/平台一致性）起步 | 交叉编码器 cross-encoder |

> 起步用「单个 SQLite 文件 = FTS5 + sqlite-vec + SQL WHERE」，零外部服务、可移植、任何平台都能读；规模上来再换独立向量库，检索接口不变。

## 8. 仓库/目录结构

```
kb/
├─ catalog/
│  └─ tags.json              # 标签目录（唯一事实源，带 version + migrations）
├─ schema/
│  └─ case.schema.json       # JSON Schema（机器校验）
├─ cases/<id>/               # 每案例一目录：meta.json + 原图/缩略图
├─ scripts/
│  ├─ ingest/                # 采集 + 解析 + 标签生成 + 落库
│  ├─ retrieve/              # 混合检索 + 重排 + few-shot 注入
│  ├─ migrate/               # 标签迁移/回填
│  └─ export/                # 导出/备份
├─ db/
│  └─ kb.sqlite              # FTS5 + sqlite-vec
└─ eval/                     # 检索评测（recall@k、认可率）
```

## 9. 接口契约（Ports，供任意模型/平台对接）

用「输入 → 输出」JSON 定义，实现可替换：

```
IngestPort        : raw page/图 + 元数据  →  DesignCase（含标签 + 向量）
RetrievePort      : query{intent, facets, semanticTags, text}  →  ranked cases[]
TagInferencePort  : 图/描述  →  {facets, semanticTags, intent}
EmbeddingPort     : text|image  →  vector[]
```

检索请求示例：

```jsonc
{
  "intent": { "platform": "xhs-3x4", "tone": ["温情治愈"] },
  "facets": { "subjectType": ["单人"], "gender": ["女"], "scene": ["户外自然"], "vertical": ["旅行攻略", "探店打卡"] },
  "semanticTags": ["旅游搭子", "结伴出游"],
  "text": "周末去海边，突出结伴出游的轻松感",
  "topK": 5
}
```

响应：`[{caseId, score, matchedFacets, matchedBy(sparse|dense), designDescription}]`。

## 12. 风险与开放问题

1. **版权**：网页设计本身有版权；仅个人本地参考、不公开传播、不商用；保留 `source.url` 便于回溯替换。
2. **标签漂移**：靠「单一事实源 + 版本 + 回填」控制；语义标签靠向量容忍近义，天然抗漂移。
3. **嵌入成本**：文本嵌入成本低；图像嵌入（CLIP）可后置，先用文本召回跑通。
4. **评测主观性**：美学/认可率人评需先做小样本 blind test 校准（沿用 PRD 既有约定）。
